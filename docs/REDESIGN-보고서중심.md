# 보고서 중심으로 다시 짜기

작성 2026-08-22 · 승인: 보고서/검토 분리 · 범위: 한 번에 전부

## 무엇이 잘못돼 있었나

심사는 **보고서를 만드는 일**인데 이 앱에는 보고서가 없었다.
접수하면 곧장 「요소 33개에 가·부 찍기」가 나왔다. 무엇을 근거로 판단하는지
알려 주는 단계가 통째로 빠져 있었다.

- 접수번호를 누르면 **감사 화면**(파일 목록)이 열렸다. 심사위원이 원하는 것이 아니다
- 시간 대조는 **과정평가형 자격이 있을 때만**, 그것도 수동으로만 돌았다
- `track_a_report.py`(막대 보고서)는 만들어져 있는데 **아무 데서도 갈 수 없었다**

## 화면에서 쓰는 말

내부 용어를 그대로 노출하지 않는다.

| 코드 | 화면 |
|---|---|
| Track A | **시간 대조** — 기록으로 확인되는 이수 시간 |
| Track B | **근거 분석** — 제출 자료에서 뽑은 판정 근거 |

## 흐름

```
접수 + 서류 수집
      │  (자동 · 결정론 · 초 단위)
      ▼
① 시간 대조 보고서    ← 접수번호를 누르면 심사 개요, 거기서 보고서
      │
      ├─ 추가 자료 없음 → 끝. 나머지는 훈련 이수
      └─ 추가 자료 있음 → [근거 분석 시작]
                              │  (AI · 6~28분)
                              ▼
                    ② 근거 분석 보고서  [보고서 보기]
                              │
                              ▼
                    ③ 전문가 검토      [검토하기]
                              │
                              ▼
                    ④ 최종 판정 기록
```

**핵심은 순서다.** ①②가 없이 ③만 있으면 「뭘 보고 뭘 판단하는지」를 알 수 없다.
보고서를 읽고 오면 검토 화면의 역할이 좁아진다 — 「이 판단들에 동의하십니까」.

## 시간 대조를 모든 접수에 돌린다

판정기(`assess_track_a`)는 시간이 어디서 왔는지 묻지 않는다.
`HeldUnit(단위코드, 시간)` 이면 된다. 그래서 근거를 둘 다 받는다.

| 근거 | 출처 | 결정론? |
|---|---|---|
| 과정평가형 자격 | `catalog_cbq_composed` 편성시간 | 예 |
| **기이수 훈련** | 훈련이수증에서 뽑은 능력단위코드·시간·평가결과 | 예 |

같은 능력단위에 둘 다 있으면 **큰 쪽**을 쓴다.
실측(R2026-0002): 훈련이수증 4건 → 410시간 중 190시간(46%) 확인.

## 만들 것

| # | 내용 |
|---|---|
| 1 | `assessment.kind` (`time` \| `evidence`) — 두 판정을 이름으로 구분 |
| 2 | 시간 대조를 기이수로도 돌게 (`held_from_prior_learning`) |
| 3 | 서류 수집이 끝나면 시간 대조 **자동 실행** |
| 4 | `/submissions/{id}` **심사 개요** — 접수번호를 누르면 여기로 |
| 5 | 시간 대조 보고서를 개요에서 열 수 있게 (기존 화면 재사용) |
| 6 | **근거 분석 보고서** — 읽기 전용, 새로 만듦 |
| 7 | 검토 화면을 입력 전용으로 정리 + 보고서로 돌아가는 길 |
| 8 | 대시보드 버튼이 상태를 말하게 |
| 9 | 보고서 인쇄 대응 (`@media print`) |

## 심사 개요 화면

```
R2026-0002 · 수동용접(CO2용접)_L4 · 총 필수 410시간

기록으로 확인 190시간 (46%) · 근거 분석 대상 220시간 · 최종 판정 전

① 시간 대조        완료
   훈련이수증 4건에서 190시간 확인          [보고서 보기]

② 근거 분석        완료 · 호출 6회
   추가 자료 7건에서 요소 33개 분석          [보고서 보기]
   (또는) 추가 자료 7건이 있습니다          [근거 분석 시작]
   (또는) 분석 중  ▓▓▓▓░░ 4/9

```

## 결과 (2026-08-22 완료)

9개 항목 모두 반영. 시험 194 → 210건.

### 만들면서 나온 것

**실측 — 시간 대조가 실제로 돈다**

| 접수 | 확인된 시간 | 근거 |
|---|---|---|
| R2026-0001 제빵_L2 | 0 / 205시간 | 편성표만 냄 — 7개 단위에 이유 기록 |
| R2026-0002 수동용접_L4 | 190 / 410시간 (46%) | 훈련이수증 4개 단위 |
| R2026-0003 SW개발_L3 | 168 / 348시간 (48%) | 훈련이수증 4개 단위 |
| R2026-0004 가금사육_L3 | 0 / 365시간 | 비NCS 수료증뿐 — 능력단위 코드 없음 |

**고친 것 넷**

1. 요소명·능력단위명을 AI 출력에서 읽고 있었다. 판정 4건 중 2건은 33·30개
   요소 **전부**에서 이름이 빠져 화면에 코드만 떴다. 이름은 기준에 있는
   값이므로 `catalog_ncs_element` 에서 찾는다.
2. 「눈여겨볼 것」이 요소마다 세어 14건이 됐다. 「파이프 용접은 담당한 바
   없습니다」 한 줄이 요소 3개에 붙은 것이다. 능력단위로 묶어 6건으로.
3. 근거 분석을 **다시 돌리는 중이면 이미 완성된 보고서가 사라졌다.**
   `case_state` 가 kind 별 최신 하나만 봐서 running 이 done 을 가렸다.
   `evidence`(최신)와 `evidence_done`(끝난 것)을 나눴다.
4. 두 Run 이 서로 다른 조회에서 오는데 `is not` 로 비교해, 실패한 적이
   없는 건마다 「다시 돌린 분석이 실패했습니다」가 붙었다.

**정책으로 올린 것**

「인정·조건부인정·불인정·보류」가 각각 무슨 뜻인지 어디에도 없었다.
이것이 「뭘 판단해야 하는지 모르겠다」의 본체다. 코드에 적지 않고
`config/rubric/v0.2.yaml` 의 `final_decision.element_decision_meanings`
에 두어 간담회에서 함께 볼 수 있게 했다.

## 아직 안 한 것

- 진행률 화면은 replay 로만 확인했다. 실제 AI 분석을 걸어 6~30분 도는
  동안의 표시는 못 봤다
- 시험 1회 실패를 봤으나(`test_unparseable_response_is_still_saved`)
  이후 8회 연속 통과해 재현되지 않았다. 원인 미상으로 남긴다
- 디자인 검토에서 미룬 항목들(디자인 시스템 4벌 분기, class 이름 충돌,
  글꼴 크기 24종, ARIA 0개)은 그대로다
