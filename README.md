# K-RPL 심사 지원 시스템

일학습병행 선행학습인정(RPL) 심사를 지원한다. **시스템은 판정하지 않는다** —
증거를 정리하고 권고를 산출하며, 최종 판정은 전문가 TF가 한다.

설계서: `../Data(20260812)/derived/docs/RPL_시스템_설계서_v1.md`

## 빠른 시작

```bash
cp .env.example .env         # 비밀값·환경별 값. 아래 설명 참고
./scripts/dev.sh env         # 무엇이 실제로 반영됐는지 확인 (키는 가려집니다)
./scripts/dev.sh db          # PostgreSQL 기동
./scripts/dev.sh migrate     # 표 생성
./scripts/dev.sh seed        # NCS 카탈로그 271만 행 적재
./scripts/dev.sh walk        # ①→⑥ 전 단계 실행 + 산출물 + 해시 대조
./scripts/dev.sh api         # http://localhost:8000/audit
```

### 앱 구동 — 매일 켜고 끄는 법 (2026-09-28)

위 「빠른 시작」은 처음 한 번(설치·표 생성·카탈로그 적재)이고, 그 뒤로는 이 셋이면 된다.
모든 명령은 `App/` 디렉터리에서 실행한다.

| 순서 | 명령 | 확인 |
|---|---|---|
| ① DB 켜기 | `./scripts/dev.sh db` | `accepting connections` 가 찍힘 (Homebrew PostgreSQL 15, 포트 5432) |
| ② API 켜기 | `./scripts/dev.sh api` (API만) 또는 `./scripts/dev.sh up` (API + 판정 워커) | http://localhost:8000/health 가 `{"status":"ok", ...}` |
| ③ 화면 열기 | http://localhost:8000/cases | 접수 현황 — 사례마다 「다음 할 일」 버튼 |

- **어느 쪽을 켜나.** 접수·판정을 터미널 스크립트(`load_candidate.py`·`assess.py`)로 돌리고 위원 페이지만 보려면 `api` 로 충분하다.
  화면의 「판정 시작」 버튼(`POST /submissions/{sid}/assess`)까지 쓰려면 워커가 있어야 하므로 `up` 을 쓴다.
- **끄기.** 터미널에서 `Ctrl+C`. DB 는 `pg_ctl -D /opt/homebrew/var/postgresql@15 stop` (켜 둬도 무방).
- **Claude Code 에서 띄울 때.** `.claude/launch.json` 의 `krpl-api` 구성(포트 8000, `--reload` 없음)을 쓴다.
  코드를 고쳤으면 서버를 **껐다 다시 켜야** 반영된다 — `dev.sh api` 는 `--reload` 라 자동 반영된다.
- **화면 주소.**

| 주소 | 무엇 |
|---|---|
| `/cases` | 접수 현황(시작점). 진행 막대는 `/cases/progress.json` 을 긁는다 |
| `/submissions/{sid}` | 심사 개요 — 단계줄·인정 시간 막대·다음 단계 링크 |
| `/assessments/{aid}/review` | Track A 위원 페이지(기록 확인 결과 + 위원 추가 인정 시간) |
| `/assessments/{aid}/panel` | Track B 위원 페이지(수행준거별 0/1/2 점수, 문서 열람창) |
| `/assessments/{aid}/plan` | Track B 확인 계획(「제출」 뒤 생성) |
| `…/review?ro=1`, `…/panel?ro=1` | 위 두 위원 페이지의 **열람 전용** — 체크박스·시간 입력이 보이되 눌리지 않고 제출이 없다. 집담회에서 위원 기기로 배포할 때(ngrok) 쓴다 |
| `/assessments/{aid}/exemption` | Track A 면제 결과(최종 판정) |
| `/audit`, `/audit/{case}` | 감사 산출물(단계별 입력·출력·해시) |
| `/stats` | 실행 비용·시간 통계 |

- **처음 설치.** Python ≥ 3.12 로 `python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"` (의존성은 `pyproject.toml`),
  `cp .env.example .env` 에 `KRPL_DATABASE_URL`·`ANTHROPIC_API_KEY` 를 넣고 위 「빠른 시작」의 `migrate` → `seed` 순서로 한 번 돌린다.
  키를 비우면 실제 호출 없이 `replay` 로 돈다. 시험은 `./scripts/dev.sh test` (DB `krpl_test` 를 따로 쓴다).
- **안 될 때.** `./scripts/dev.sh env` 로 반영된 설정을 본다. 포트 8000 이 이미 쓰이면 `lsof -i :8000` 으로 이전 서버를 찾아 끈다.
  DB 가 안 뜨면 `/tmp/pg15.log` 를 본다.

### 위원 심사 한 건 돌리기 (4·5차 집담회 흐름, 2026-09-24 기준)

```bash
./scripts/dev.sh db && ./scripts/dev.sh up        # DB + API(8000) + 워커
# ① 접수 — 검토용 docx 폴더를 그대로 받는다 (파일명으로 종류 추정, 00_* 제외)
.venv/bin/python scripts/load_candidate.py --src "../워크숍/3차 워크숍/T4_TrackB_사례세트/case2_.../검토용_문서" \
    --case R2026-9302 --program 건축설계_L3
# ② 판정 — Track A 는 접수 때 자동. Track B(AI) 는 명시적으로 (Haiku, 건당 $1.1~1.4 · 6~8분)
.venv/bin/python scripts/assess.py R2026-9302            # --profile trackb_assess_opus 로 Opus
# ③ 위원 페이지 — 브라우저에서 수행준거 점수 0/1/2 를 고친다 (즉시 재계산·자동 저장)
#    Track A: http://localhost:8000/assessments/{aid}/review   Track B: http://localhost:8000/assessments/{aid}/panel
#    aid 는 심사 개요(/submissions/{sid}) 또는 /cases 에서 찾는다.
# ④ 「제출 → 확인 계획」 버튼 → 보류 단위 확인 계획 (AI 1회, $0.07) → /assessments/{aid}/plan
```

실제 호출 없이 돌려 보려면 `KRPL_LLM_BACKEND=replay`(저장본 재생). 위원 페이지는 서버 없이 정적 파일로도 열리지만 저장·제출은 안 된다.

### 환경 설정 (`.env`)

`.env.example` 를 복사해 씁니다. 심사 기준·프롬프트·모델 파라미터는 여기가 아니라
`config/` 아래에 있습니다. `.env` 에는 **비밀값과 환경마다 달라지는 값**만 둡니다.

| 변수 | 뜻 |
|---|---|
| `KRPL_ENV` | `local` · `staging` · `prod` · `test` → `config/environments/{값}.yaml` 을 덧씌움 |
| `KRPL_DATABASE_URL` | PostgreSQL 접속 문자열 |
| `KRPL_LLM_BACKEND` | `anthropic`(실제 호출) · `replay`(저장본 재생, 비용 0). 비우면 키 유무로 자동 |
| `ANTHROPIC_API_KEY` | Claude API 키. 비어 있으면 실제 호출은 일어나지 않습니다 |
| `KRPL_REPLAY_DIR` | 재생용 산출물 위치. 비우면 `tests/fixtures/trackb/` |

우선순위는 `config/settings.yaml` < `config/environments/{env}.yaml` < `.env` < 실행 시 환경변수.
그때그때 준 값이 가장 셉니다 — 실수로 과금되는 걸 막으려면
`KRPL_LLM_BACKEND=replay ./scripts/dev.sh assess R2026-0002` 처럼 못박으면 됩니다.

`KEY=` 처럼 **빈 값은 「설정하지 않음」**으로 봅니다.
`.env` 는 어느 디렉터리에서 실행하든 `App/.env` 를 읽고, `.gitignore` 에 들어 있습니다.

> `.env` 는 한때 **조용히 무시됐습니다.** `pydantic-settings` 의 `env_file` 은
> `Settings` 필드에만 닿고 `os.getenv` 로 읽는 값(`ANTHROPIC_API_KEY`·`KRPL_LLM_BACKEND`)에는
> 닿지 않아서, 키를 넣어도 재생 백엔드로 돌았습니다.
> 지금은 `krpl_core/config.py` 가 `.env` 를 `os.environ` 에 실어 줍니다.
> `tests/unit/test_env.py` 가 별도 프로세스로 실제 기동을 확인해 재발을 막습니다.

## 설계 원칙

**1. 기준은 코드가 아니라 설정이다.**
심사 기준의 모든 숫자와 규칙은 `config/rubric/*.yaml` 에 있다.
간담회에서 값이 정해지면 YAML 한 줄을 바꾼다. 프로그램은 손대지 않는다.

**2. 미확정 기준으로는 판정하지 않는다.**
아직 정해지지 않은 항목은 `pending_decisions` 에 색인되고,
`rubric.is_decided(key)` 로 판정 전에 게이트를 건다.
운영 환경(`prod`)에서는 미확정 항목이 있으면 **기동 자체를 거부**한다.

**3. 재현성.**
모든 판정 기록에 `rubric_version` · `model` · `input_hash` 를 남긴다.
기준이 바뀌어도 과거 심사가 어느 기준으로 판정됐는지 설명할 수 있다.

**4. 근거 추적.**
판정마다 근거를 `evidence` 에 기록한다. 기록 확인는 어느 자격·이수증의 어느
능력단위인지, 근거 분석은 어느 문서의 어느 조각(fid)인지 — 원문 대조가
가능해야 한다. 두 판정은 `assessment.kind`(`time`·`evidence`)로 구분한다.

**5. 마스킹은 지우기 전에 지켜야 할 것을 먼저 정한다.**
개인정보 정규식은 과잉 탐지가 과소 탐지보다 위험하다.
실제로 `2025-02-11` 같은 날짜가 계좌번호로 오탐돼 작업일지의 시점 정보가
전부 소실된 적이 있다. 판정 근거가 사라지는 사고다.
`tests/unit/test_masking.py` 의 `MUST_KEEP` 목록이 이 회귀를 막는다.
패턴을 고칠 때는 반드시 이 목록을 먼저 늘린다.

## 문서 수집 (2단계)

```
POST /submissions/{sid}/documents     파싱 → 마스킹 → 조각화 → 저장
GET  /submissions/{sid}/fragments     조각 조회 (doc_key 로 필터)
```

문서 하나가 조각(fragment) 여러 개로 쪼개지고, 조각마다 고정 식별자가 붙는다.

| 항목 | 값 |
|---|---|
| 조각 식별자 | `D03-S07` = 3번 문서의 7번째 조각 |
| 문서 서술형식 | `narrative` · `record` · `dated` · `list` (자동 판별) |
| 진술 유형 | `직접수행` · `부정` · `불확실` · `관찰·간접` |
| 신뢰도 등급 | 문서에 부여된 A~E 가 조각에 그대로 상속 |

`부정` 으로 분류된 조각은 3단계에서 지지 근거보다 우선한다
(기준서 R8 — "안 했다"는 진술은 "했다"는 진술을 이긴다).

**기이수 교육과정 추출** — 훈련이수증에서 능력단위코드·이수시간·평가 여부를 뽑는다.
`평가` 문구가 없거나 `평가 미실시` 로 적힌 항목은 `evaluated=false` 가 되고,
이는 R0(기이수인정)의 게이트로 쓰인다. 편성표만 제출된 경우가 여기 걸린다.

실제 4건에 대한 수집 결과:

| 심사번호 | 종목 | 문서 | 조각 | 기이수 | 평가확인 |
|---|---|---|---|---|---|
| R2026-0001 | 제빵_L2 | 6 | 32 | 7 | 0 (편성표만 → R0 불가) |
| R2026-0002 | 수동용접_L4 | 7 | 30 | 4 | 4 (R0 대상) |
| R2026-0003 | SW개발_L3 | 6 | 30 | 4 | 4 (R0 대상) |
| R2026-0004 | 가금사육_L3 | 7 | 28 | 0 | 0 (비NCS 과정) |

파일 한 건이 깨져도 나머지는 수집된다. 실패는 응답의 `warnings` 로 돌려준다.

```bash
./scripts/dev.sh demo      # 위 4건을 다시 수집
./scripts/dev.sh ingest    # 문서 수집 워커
```

## Track B 판정 (3단계)

```
POST /submissions/{sid}/assess        판정 시작 (문서 수집 후)
GET  /assessments/{aid}               결과 — 응답의 `track` 으로 A·B 구분
GET  /assessments/{aid}/validation    기계 검증 이력
```

### 흐름 — 능력단위마다 따로 부른다

```
패키지 조립 ─┬→ 능력단위 A ─→ LLM ─→ 검증 ─통과─┐
  (결정론)   ├→ 능력단위 B ─→ LLM ─→ 검증 ─통과─┤
             ├→ …                             ├→ 합치기 → 전체 재검증 → 저장
             └→ 능력단위 J ─→ LLM ─→ 검증 ─실패─┘        (+ 전체 소견 종합 호출)
                                    └→ 그 단위만 재요청 (최대 3회)
```

**틀린 능력단위만 다시 받는다.** 예전에는 요소 하나가 틀려도 33개를 통째로 다시 받았다 —
실호출에서 KSA 하나 빠진 것 때문에 $1.3 를 버렸다.

지원자 자료는 **캐시되는 자리(system 블록)** 에 둔다. 청크마다 그대로 반복되므로
두 번째부터 10% 가격이 된다.

```
system [캐시]  분석지침 · 기준요약 · 지원자 자료(문서·조각·기이수)   9,367 토큰
user           이 능력단위의 NCS 요구사항만                      약 2,000 토큰
```

| | 단일 호출 | 청크 10회 | 청크 + 캐시 |
|---|---:|---:|---:|
| 입력 토큰 | 29,654 | 114,227 (3.9배) | **38,354 (1.3배)** |
| 출력 토큰 | 38,000 | 38,000 | 38,000 |
| 비용 | $1.098 | $1.521 | **$1.142** |
| 재시도 1건 | 전체 재생성 $1.3 | 그 단위만 | **$0.12** |
| 잘림 위험 | 출력 58k/120k | 청크당 4k 수준 | 사실상 없음 |
| 작은 모델 | 입력 30k·출력 38k 필요 | **입력 11k·출력 4k** | 가능 |

패키지의 79% 가 NCS 요구사항이라 **반복이 아니라 분할된다.** 그래서 10배가 아니라 3.9배다.

청크 간 맥락이 끊기는 손실은 **전체 소견을 별도 호출로 종합**해 메운다
(`assessment.synthesize_overall`). 요소별 권고·사유만 모아 보내므로 입력도 출력도 작다.

합친 결과는 **전체 패키지로 다시 검증한다.** 청크별 통과만으로는
능력단위 하나가 통째로 빠진 것을 잡을 수 없기 때문이다.

`chunk_by: none` 으로 두면 예전처럼 한 번에 부른다 — 비교용으로 남겨 두었다.

**AI에게 「검증했느냐」고 묻지 않는다.** 스스로 통과했다는 보고는 믿을 수 없다.
`krpl_rules/track_b.py` 가 산출물을 원문과 직접 대조한다. 확인하는 것은 세 가지다.

| 확인 | 대표 검사 |
|---|---|
| **인용 환각** | 없는 조각(fid) 인용 · `quote` 가 원문의 연속 부분문자열인지 |
| **누락** | 능력단위요소 전수 · KSA 전수 배정 (근거 아니면 미확보, 둘 중 하나) |
| **기준 위반** | R1 기간보증 A·B 필요 · R8 부정 우선 · 요소당 대면평가 1건 · R0 성립요건 |

검증에 걸리면 지적 사항을 **고칠 수 있을 만큼 구체적으로** 적어 되돌려준다
(`config/prompts/trackb_repair.md`). 일부 수정이 아니라 전체를 다시 받는다.

### 오류와 경고는 다르게 다룬다

- **오류** — 재요청한다. 3회 안에 통과 못 하면 `manual_review` 로 두되 산출물은 저장한다.
  전문가가 볼 것이 아무것도 없는 상태가 가장 나쁘다.
- **경고** — 멈추지 않는다. 대표적으로 **미확정 기준에 걸린 R1**
  (쟁점 4 — KSA 커버리지 하한 미정)은 해당 요소에 `needs_expert_review` 를 붙이고 진행한다.
  간담회 확정 전이라고 시스템을 못 쓰게 만들지 않는다.

### 구조화 출력(JSON 스키마 강제)은 쓰지 않는다 — 실측으로 확인

`config/schemas/assessment_output.json` 를 `output_config.format` 으로 보내려 했으나
API 가 세 번 연속 거부했다 (2026-08-21 실호출).

| 시도 | 응답 | 조치 |
|---|---|---|
| ① | `object 마다 additionalProperties 를 false 로 명시해야 함` | 누락 1곳 수정 |
| ② | `union 타입 21개 — 한도 16개` | 21 → 0 으로 재구성 |
| ③ | **`compiled grammar is too large`** | 더 줄일 방법 없음 |

요소당 필수 항목 18개 × 중첩 배열이라 문법이 플랫폼 한도를 넘는다.
더 깎으면 계약만 약해지고 통과 보장도 없다.

**끄되 계약은 그대로 지켜진다.** 형식 강제보다 `krpl_rules/track_b.py` 의 검증이 훨씬 강하다 —
인용문을 원문과 글자 단위로 대조하고, KSA 전수 배정과 기준서 철칙까지 본다.
스키마 파일은 계약 문서로 남겨 둔다.

`AnthropicClient` 에는 스키마가 거부되면 형식 제약 없이 한 번 더 가는 폴백이 있다.
이 폴백이 실제로 첫 실호출을 살렸다. `structured_output` 을 다시 켤 경우를 대비해 남겨 둔다.

### 방식·effort 는 실행할 때 바꿀 수 있다

```bash
./scripts/dev.sh assess R2026-0002 --force                              # 기본값 (청크 · claude-haiku-4-5)
./scripts/dev.sh assess R2026-0002 --force --chunk-by none              # 한 번에 전부
./scripts/dev.sh assess R2026-0002 --force --profile trackb_assess_opus # claude-opus-5 · effort medium (이전 기본값)
./scripts/dev.sh assess R2026-0002 --force --profile trackb_assess_high # claude-opus-5 · effort high
```

**2026-09-23부터 기본 모델은 `claude-haiku-4-5`** (별칭. 스냅샷 `claude-haiku-4-5-20251001`, 출력 한도 64,000, $1/$5 per MTok).
Haiku 4.5 는 `output_config.effort` 를 받지 않으므로(400) 프로파일에 `effort: null` 을 두고, `thinking` 은 adaptive 가 아니라
`{type: enabled, budget_tokens: 16000}` 방식이다. `krpl_core/llm.py` 는 effort 가 비어 있으면 `output_config` 자체를 보내지 않는다.
아래 실측 표(2026-08-22)는 모두 Opus 기준이며 Haiku 실측은 아직 없다.

기본값은 `config/settings.yaml` 의 `assessment.chunk_by` 와
`config/models.yaml` 의 `trackb_assess` 프로파일에 있다.
`--chunk-by` · `--profile` 은 그 실행에만 적용되므로 설정 파일을 건드리지 않고 비교할 수 있다.

### LLM 백엔드는 환경변수 하나로 바꾼다

| `KRPL_LLM_BACKEND` | 동작 | 비용 |
|---|---|---|
| `replay` | 저장된 산출물 재생 (`tests/fixtures/trackb/`) | 0 |
| `anthropic` | 실제 호출. `ANTHROPIC_API_KEY` 필요 | 아래 실측 |

지정하지 않으면 키가 있을 때 `anthropic`, 없으면 `replay` 다.
모델·effort·캐시·타임아웃·요금표는 전부 `config/models.yaml` 에 있다.

### 보고서 포맷은 연구팀이 확정한 것이다

`docs/formats/` 에 원본 두 벌(`trackA_보고서.html`·`trackB_보고서.html`)을
그대로 두었다. 회람·확정된 포맷이므로 **보기 좋게 만들려고 임의로 바꾸지
않는다.** CSS 변수·클래스명·마크업 구조·범례 문구·아이콘·색을 그대로 옮겼고,
`tests/integration/test_report_format.py` 32건이 원본 파일과 구현을 나란히
대조한다. 원본에 없는 것을 요구하면 시험 쪽이 틀린 것으로 잡힌다.

원본은 시나리오·지원자 여럿을 한 문서에 늘어놓은 설계 시안이고, 앱은 접수
한 건을 그린다. 그 차이(문서 하나 = 카드/섹션 하나)만 다르다.

**Track A — 가로 막대**
- 척도는 카드 안에서 공통: `max(요구, 이수)` 전체 최대값.
  행마다 따로 잡으면 막대 길이를 서로 견줄 수 없다
### 위원 페이지 — 한 지원자 = 한 쪽 (2026-09-23, 1~3차 TF 반영)

### 판정 단위는 수행준거다 (2026-10-02, 4차 TF 반영)

4차 TF(9/30): 「KSA 항목을 세는 것은 NCS 취지와 다르다 — 수행준거(「…할 수 있다」)로 보라. 절반 넘으면 인정은 너무
느슨하다 — 빈 수행준거가 없어야 하고 전체도 문턱을 넘어야 한다.」 그래서 Track B 의 판정 단위를 바꿨다.

| 층 | 규칙 | 출처 |
|---|---|---|
| 수행준거 점수 | **2** = 직접 근거 1건 이상 · **1** = 직접 없고 간접만 · **0** = 근거 없음 또는 부정 진술. 존재 기준 — 근거가 많아져도 내려가지 않는다. 위원이 0/1/2 를 고치면 위원 값 우선 | rubric `track_b.pc_scoring` |

  요소마다 `schema:"pc"`. 검증기는 형식을 보고 구형(ksa_ref)도 그대로 검증한다.
- 계산은 `services/review/coverage.py` 의 `pc_score` → `element_scores` → `unit_by_scores`, 단위 하나의 입구는
  `unit_verdict_of`(형식 pc / ksa / mixed). `unit_verdicts()` 의 키는 유지 + `mean`·`n_zero`·`format`.

- 위원 페이지(`track_b_panel.py`): 단위 → 수행준거 두 층(요소명은 캡션). 서버가 AI 점수를 페이지에 넣어 주고 JS 는

#### 이전 규칙 (2026-09-24 ~ 10-01, 구형 판정을 읽을 때만)

- **능력단위 판정은 인정된 항목(지식·기술·태도)의 비율로 낸다** (`coverage.unit_by_coverage`): 요소 커버리지 평균이
  50% 이상 인정 · 30% 이상 보류 · 미만 불인정. 위원 판정 라디오는 없다 — 판정은 항목에서 따라 나온다.
  근거마다 AI 가 적합도 `fit` 를 매긴다(2026-09-24, rubric `output_vocabulary.evidence_fit`, 검증기가 필수로 잡음):
  **직접** → 인정(위원이 「근거 부적합」으로 뺄 수 있음) · **간접** → 불인정이되 근거를 보여 주고 위원이 「위원 인정」할 수 있음 ·
  **부정**(못 한다·안 해봤다는 진술) 또는 근거 없음 → 불인정, 검토란 없음(위원 부담 최소화).
  항목 인정 = 직접 근거가 있고 위원이 빼지 않은 것 + 간접 근거를 보고 위원이 인정한 것. fit 이 없는 옛 결과는 직접으로 본다.
  항목 전체는 catalog_ncs_ksa(수행준거마다 반복되는 같은 항목은 하나로) 기준.
  위원 표시는 `element_review.excluded_evidence` 에 요소별로 저장: 뺀 근거 fid · `add:<항목>`.
  능력단위 판정 = 요소별 인정 항목 비율의 평균(50% 인정 · 30% 보류). 3차 TF 의 척도/질문 방식은 근거 없이 판단하기 어려워 2026-09-23 화면에서 뺐다.
  부정 진술은 요소를 통째로 미인정시키지 않는다(2026-09-23, rubric R8 off). 2026-09-24부터는 해당 항목의 근거로 `fit:"부정"` 으로 붙어 그 항목만 불인정이 된다.
  화면의 문서명·인용을 누르면 오른쪽 열람창에 그 문서 전문이 열리고 해당 문장이 강조된다(조각 JSON 을 페이지에 내장, 서버 호출 없음).
- **제출 → 확인 계획** (2026-09-24): 위원 페이지의 「제출」(`POST /assessments/{aid}/panel/submit`)이 위원 표시를 반영한 단위 판정을
  artifact(stage `panel`)에 남기고, 보류 단위의 미확인 항목만 모아 AI 1회(`trackb_plan` 프로필, Haiku, 실측 $0.07)로 문안을 받아

### 두 트랙은 각자 단계줄을 갖는다 (2026-09-24)

```
Track A   ① 기록 확인   ② 근거 분석   ③ 전문가 검토   ④ 최종 판정
Track B   ① 근거 분석   ② 위원 검토   ③ 확인 계획     ④ 최종 판정
```

Track B 에는 ① 기록 확인이 없다 — 코드가 맞는 이수 기록이 없는 것이 전제이므로
근거 분석이 곧 판정이다. 기록 확인은 모든 접수 건에 자동으로 돌지만, Track B 개요에서는
번호 없이 「참고」로만 보인다.

| Track B 단계 | 화면 |
|---|---|
| ① 근거 분석 | `/assessments/{aid}/report` — 연구팀 회람본 그대로의 세 장 |
| ② 위원 검토 | `/assessments/{aid}/panel` — 수행준거별 점수 |
| ③ 확인 계획 | `/assessments/{aid}/plan` — 보류 단위의 시험·시연·면접 배정 |
| ④ 최종 판정 | `/assessments/{time_aid}/exemption` — 면제 시간 |

**위원 페이지는 개요 어디에서도 연결되지 않았다.** 판정 엔진이 다 돌아가는데 위원이

때문이다. 이제 트랙에 따라 카드의 목적지와 단계줄이 갈라진다.

쓰는 함수를 읽는다.

| | 출처 | 규칙 |
|---|---|---|
| Track A | `unit_hours.unit_gaps()` | 이수 + 위원 인정이 요구의 50% 이상 → 요구시간 전체 |
| Track B | `coverage.unit_verdicts()` | 수행준거 전부 ≥1 이고 평균 ≥1.5 → 요구시간 전체 (2026-10-02; 구형 판정은 요소 비율 50%) |

`unit_verdicts()` 는 위원 페이지가 화면 안에서 세던 것을 꺼낸 것이다. 두 화면이 같은
함수를 읽으므로 면제 결과와 위원 페이지가 다른 시간을 말할 수 없다.

### 「Track A/B」는 두 가지를 가리킨다 — 화면이 갈라 적는다 (2026-09-24)

| | 뜻 | 저장 | 값 |
|---|---|---|---|
| **접수 구분** | 이 사람을 어떤 경로로 심사하나 | `submission.track` | `A` · `B` |
| **판정 종류** | 어떤 판정을 돌렸나 | `assessment.kind` | `time` 기록 확인 · `evidence` 근거 분석 |

보고서 제목 「RPL Track A/B 심사 보고서」는 **판정 종류**이고 연구팀 확정 포맷이라 고칠 수 없다.
그래서 접수 구분은 제목이 아니라 **배지**로 따로 적는다. A 로 접수한 건에서 Track B 보고서를
보고 「내가 A 로 한 것이 맞나」를 확인할 길이 없던 것을 고쳤다.

```
A 자격   과정평가형 자격 보유 — 기록 확인
B 서류   경력·훈련 등 제출 서류 기반 — 근거 분석
```

홈 · 접수 현황 · 심사 개요 · 서류 올리기 · Track A/B 위원 페이지 · 면제 결과에 모두 붙는다.
문구는 접수 화면의 선택지에서 그대로 가져왔다 — 고른 말과 보이는 말이 다르면 같은 것인지 알 수 없다.
어휘는 `services/report/_shared.py` 의 `TRACK` 한 곳.

### 부족한 단위는 위원이 메운다 — 면제는 게이트다 (2026-09-24)

**Track A 와 B 는 접수부터 다른 경로다.** 근거 분석은 B 가 아니라 **Track A 안의 2단계**다.

```
Track A  ① 기록 확인   NCS 코드 비교 → 능력단위별 이수시간
         ② 근거 분석   그 밖의 자료로 추가 인정이 가능한지 (심사자가 결정)
         ③ 최종 판정   인정시간 → 인정 능력단위 → 면제시간
Track B  비NCS 학습·경력 — 별도 경로
```

셈은 이렇다.

```
인정시간 = min(이수, 요구) + 위원 추가 인정
비율     = 인정시간 ÷ 요구시간
면제시간 = 비율 ≥ 50% 이면 요구시간 전체, 미만이면 0
```

**합산이 아니라 게이트다.** 45h 를 인정했다고 45h 가 면제되지 않는다.

```
요구 80h · 이수 20h · 위원 +25h = 45h (56%)  →  면제 80h
요구 80h · 이수  0h · 위원 +20h = 20h (25%)  →  면제  0h
요구 80h · 이수  0h · 위원 +39h = 39h (49%)  →  면제  0h   ← 한 시간 차이로 갈린다
요구 80h · 이수  0h · 위원 +40h = 40h (50%)  →  면제 80h
```

기준을 새로 만든 것이 아니다. `rubric.track_a.verdicts` 의 `조정범위내 ratio_gte: 0.5`
— 훈련기준 「−50%까지 조정 가능」 조항 — 을 **이수시간이 아니라 최종 인정시간**에 적용한 것이다.
게이트 값은 코드에 박지 않고 기준서에서 읽는다(`credit_floor()`).

|---|---|
| 셈 | `services/review/unit_hours.py` 한 자리 (`counted`·`ratio_final`·`credited`·`to_pass`) |
| 저장 | `element_review.granted_hours` — 기록 확인 판정의 element_id 가 능력단위 코드다 |
| API | `POST /assessments/{aid}/units/hours` · `GET /assessments/{aid}/exemption` |
| 화면 | Track A 위원 페이지의 표 — 요구·이수·현재·위원 추가·최종·면제. 「인정선까지 +20h」 안내 |
| 근거 | 최신 근거 분석 판정(검증 미통과 포함)에서 `catalog_ncs_element.unit_code` 로 단위에 잇는다 |

**같은 인용은 묶는다.** 한 문장이 KSA 항목마다 되풀이돼 한 단위에서 같은 부정 진술이
**41번** 나왔다. 인용·출처·적합도가 같으면 한 줄로 접고 「항목 N곳에 같은 자료」로 적는다.

**단계 이름을 제목 위에 붙인다.** 확정 보고서 제목(「RPL Track A/B 심사 보고서」)은
연구팀 회람본이라 못 바꾸므로(`docs/formats/README.md`), 그 위에 `① 기록 확인`·`② 근거 분석`·
`③ 최종 판정` 을 크게 적고 확정 제목은 작게 아래로 내린다. Track A 건에서 근거 분석을 열었을 때
「왜 갑자기 Track B 가 되지」 하던 것을 이렇게 푼다. 어휘는 `_shared.py` 의 `STEP`.

### 판정은 인정 / 보류 / 불인정 세 묶음이다 (2026-09-23, 2차 TF 반영)

능력단위마다 이수시간 ÷ 요구시간의 비율로 다섯 판정 중 하나를 고르고(`rubric.track_a.verdicts`),
보고서와 집계는 `rubric.track_a.buckets` 로 세 묶음으로 접는다.

| 비율 | 판정 | 권고 | 묶음 | 뜻 |
|---|---|---|---|---|
| ≥ 100% | 완전충족 | R0 | **인정** | 그 단위 요구시간 전체 감면 |
| ≥ 50% | 조정범위내 | R0 | **인정** | 고시 「−50% 조정」 조항 — 역시 요구시간 **전체** 감면 (운영매뉴얼 규칙) |
| ≥ 30% | 보류 | R4 추가서류 | **보류** | 부족 시간·이유와 `hold_evidence` 목록(제출 여부 표시)을 안내하고 위원이 판단 |
| > 0% | 시간부족 | R5 훈련 | **불인정** | 30% 미만 — 자동 불인정 |
| 없음 | 미이수 | R5 훈련 | **불인정** | 코드 불일치 |

- 보류 구간(30~50%)은 2차 TF 제안이며 **미확정**(`pending_decisions`). 대안 「자격 단위 인정」을 적용한
  인정 시간(인정+보류)을 보고서가 참고값으로 함께 보인다.
- 「확정 인정률」(`credit_rate_strict`, 100% 채운 단위만)은 규칙에 없는 더 엄격한 수치라 **참고값**으로 내렸다.
  인정률은 `credit_rate_adjusted` = 인정 묶음 ÷ 총 필수시간이다.
- 50% 미만 단위를 판정 전에 걸러내지 않는다. 전에는 `eligible_units()` 가 걸러 「갈음불가」로 빠지고
  막대에는 미이수(○)로 나왔다. 지금은 `held_units_for_time_check()` 가 전부 넘기고 판정기가 보류/시간부족으로 가른다.
  `eligible_units()` 는 Track B 의 R0 확정에만 쓴다.
- 명령줄 접수(`scripts/load_candidate.py`)가 `신청서.yaml` 의 **보유자격**을 `과정평가형자격` 문서 행으로 넣는다
  (화면 접수와 같은 방식). 전에는 무시해서 자격 편성기준 경로가 빠졌다 — A3 사례 실측 45% → 고친 뒤 55%.

- 빨간 실선 = 요구시간, 점선 = −50% 하한
- 색만으로 뜻을 전하지 않는다 — 적록색약(deutan)에서 초록·빨강은 ΔE 4.1로
  구분이 어렵다. 아이콘(●▲■○) + 상태 텍스트를 상시 표기하고 시간부족엔 빗금
- KPI 4종: 능력단위 커버리지 / 인정 시간 — 확정 / 조정 적용 시 / 추가 훈련·확인
  커버리지 100%인데 확정 인정률 0%인 경우가 있어 **둘을 함께 읽어야 한다**

**Track B — 격자 히트맵 + 세 장**
```
Ⅰ. 히트맵      가로축 능력단위(요구시간 순) · 세로축 요소 번호(큰 번호가 위)
Ⅱ. 보완계획    추가서류·면접·실기·훈련. 같은 항목은 병합
Ⅲ. 판정 근거   요소별 소견·근거 인용·부정 진술·자료 상충·보완 방법
```
아이콘 R0 ★ · R1 ● · R2 ▲ · R3 ■ · R4 ◆ · R5 ○. 빈 칸은 `.hc.empty`.

Ⅱ에서 **같은 항목은 병합한다.** 「안전보건교육 이수확인서 한 건」이 요소
열 곳에 걸리는 일이 흔한데, 요소마다 적으면 지원자가 열 번 준비해야 하는
것처럼 보인다.

### 전문가 검토는 다섯 단계다

요소 서른셋에 한꺼번에 가·부를 찍으라고 하면 무엇부터 볼지 알 수 없다.
심사는 원래 순서가 있는 일이다.

```
1 인정 여부 검토   제출 자료만으로 판단할 수 있는 것 (판단 대상만)
2 추가 서류        서류를 더 받으면 풀리는 것        (없으면 건너뜀)
3 면접             질문지 — 질문 · 왜 이 방법인가 · 응답에 담겨야 할 것
4 실기             과제 목록 + 결과 입력
5 최종 결과        무엇이 얼마나 인정됐고 무엇 때문인지
```

**종합 현황 대시보드(Track B 보고서의 히트맵까지)가 모든 단계 위에 붙는다.**
단계를 넘길 때마다 갱신된다 — 항목에 통과를 찍어도 그것이 전체에서 무슨
뜻인지 보이지 않으면 찍을 이유가 없다. 인정 초록 · 미인정 빨강 · 아직 회색.

**보완 항목은 요소가 아니라 항목 단위로 다룬다.** 「안전보건교육 이수확인서」
한 건이 5개 능력단위 15개 요소를 한꺼번에 푼다. 요소마다 물으면 같은 서류를
열다섯 번 확인하는 꼴이 된다.

**결과는 계산이다.** 항목을 통과했으면 그 항목이 채우기로 한 KSA 가 채워진
것이므로 요소 인정을 따로 누를 것이 없다. 한 요소에 면접·실기가 둘 다
걸렸으면 둘 다 통과해야 한다. 「무엇을 보고 그렇게 됐는지」는 5단계 줄마다
적고 감사 기록에도 남긴다.

**질문지는 AI 에게 다시 묻지 않는다.** 목적은 그 항목의 `reason`, 응답에
담겨야 할 것은 대상 KSA 의 고시 원문 이름이다. 둘 다 이미 있는 값이다.

계산은 `services/review/stages.py` 한 자리. 인정 시간이 Track A 기록 확인과
어긋나지 않는지를 시험이 지킨다(실측 190/410h 일치).

### 보고서는 다 싣고, 검토는 추린다

보고서는 요소를 빠짐없이 싣는다. 그래야 근거가 된다. 그러나 사람이 판단할
것은 그중 일부다 — 실측으로 33개 중 15개가 훈련이수증으로 확정돼 판단할
여지가 없었다. 그 15개까지 한 줄씩 누르게 하면 정작 따져야 할 18개에 쓸
힘이 흩어진다.

선별 규칙은 `services/review/triage.py` 한 자리에만 둔다.

| 갈래 | 뜻 |
|---|---|
| `look` | 먼저 보실 것 — 결정과 **어긋나는** 자료가 있다 |
| `judge` | 판단이 필요한 것 |
| `settled` | 기록으로 확정된 것 — 묶음째 확인만 |

`look` 을 「부정 진술이 있음」으로 잡으면 절반이 걸려 선별이 되지 않는다
(33개 중 17개였다). 결정과 어긋나는 것만 골라낸다 — 예: 훈련 기록으로
기이수 확정됐는데 반장 확인서에는 「그 자세는 담당한 적 없다」.

### 심사는 보고서를 만드는 일이다

처음에는 접수하면 곧장 「요소 33개에 가·부 찍기」가 나왔다. 무엇을 근거로
판단하는지 알려 주는 단계가 통째로 빠져 있었고, 접수번호를 누르면 감사
화면(파일 목록)이 열렸다. 심사위원이 원하는 것이 아니다.

그래서 **읽는 자리와 판단하는 자리를 나눴다.** 보고서를 읽고 오면 검토
화면의 역할이 좁아진다 — 「이 판단들에 동의하십니까」.

| 코드 | 화면에서 쓰는 말 |
|---|---|
| Track A | **기록 확인** — 기록으로 확인되는 이수 시간 |
| Track B | **근거 분석** — 제출 자료에서 뽑은 판정 근거 |

### 기록 확인는 모든 접수 건에 자동으로 돈다

판정기(`assess_track_a`)는 시간이 어디서 왔는지 묻지 않는다. `HeldUnit`
이면 된다. 그래서 근거를 둘 다 받는다.

| 근거 | 출처 |
|---|---|
| 과정평가형 자격 | `catalog_cbq_composed` 편성시간 |
| 기이수 훈련 | 훈련이수증에서 뽑은 능력단위코드·시간·평가결과 |

같은 능력단위에 둘 다 있으면 큰 쪽을 쓴다. 예전에는 자격이 있을 때만
돌았고, 접수 4건 모두 자격이 없어 한 건도 돌지 않았다.

**「0시간」일 때가 오히려 중요하다.** 그것만 보여 주면 서류를 안 낸 것인지
냈는데 안 쳐 준 것인지 구분할 수 없는데, 그 둘은 다음에 할 일이 다르다 —
편성표만 낸 사람에게는 이수증을 받으면 되고, 아예 없는 사람은 근거 분석으로
간다. `rejected_units()` 가 이유를 남긴다.

### 「지금 어디까지 왔나」는 한 곳에서만 답한다

같은 질문을 대시보드와 개요 화면이 각자 SQL 로 답하면 반드시 어긋난다.
`services/assess/case_state.py` 가 유일한 답이고, 두 화면 모두 여기서 읽는다.

`evidence`(최신 실행)와 `evidence_done`(끝난 것)은 나눠 둔다. 새 분석이
도는 중이라도 이미 나온 보고서는 계속 열려야 한다.

### 개요의 막대는 검토 결과까지 읽는다

기록 확인 결과만 읽었더니, 전문가가 100시간을 더 인정한 뒤에도
「아직 확인되지 않은 시간」이 그대로였다.

    실측 R2026-9002 — 총 450시간
      기록 확인 150 + 전문가 판단 100 = 인정 250
      화면은 「아직 확인되지 않은 시간 300시간」이라 적고 있었다 (맞는 값은 200)

총 필수 시간을 다섯 칸으로 가른다(`ReviewContext.hour_split()`). 합은 언제나
총 필수 시간이고, 시험이 그것을 지킨다.

| 칸 | 뜻 |
|---|---|
| 기록 | 이수 기록만으로 단위 전체가 확정된 시간 — Track A 값과 같다 |
| 전문가 | 사람이 판단해 더 인정한 시간 |
| 미판단 | 아직 1단계 판단이 안 된 시간. 여기서 무엇을 면접·실기로 볼지 갈린다 |
| 대기 | 면접·실기·추가서류 결과를 기다리는 시간 |
| 훈련 | 확인으로는 풀리지 않아 훈련으로 채워야 하는 시간 |

단위 시간은 그 단위의 요소가 **전부** 인정돼야 붙는다
(`unit_credit_rule: all_elements`, 쟁점 D-7 미확정). 요소 하나가 대기면
단위 시간 전부가 대기다.

### 2단계 결과가 3·4단계로 흐른다

AI 는 요소마다 「비어 있는 KSA」를 서류·면접·실기로 **쪼개서** 배정한다.
실측 5건에서 (요소, KSA) 겹침이 0이었다 — 셋은 서로 다른 것을 맡고,
셋 다 통과해야 요소가 인정된다.

| 심사번호 | KSA칸 | 서류 | 면접 | 실기 | 서류∩면접 | 서류∩실기 |
|---|---|---|---|---|---|---|
| R2026-9002 | 343 | 62 | 19 | 159 | 0 | 0 |
| R2026-0002 | 162 | 37 | 28 | 43 | 0 | 0 |
| R2026-0001 | 178 | 95 | 11 | 48 | 0 | 0 |

**받으면 다시 본다.** 2단계에서 서류를 받으면 파일을 올린다. 조각으로
수집한 뒤, 그 서류가 풀려던 요소만 다시 판정한다
(`run_track_b(keep_from=…, focus=[…])`). 나머지 요소와 이미 내려진 검토
판단은 그대로 옮긴다 — 서류 한 장 때문에 서른세 개를 처음부터 다시
판단하게 하지 않는다. 다시 볼 요소의 판단만 뺀다. 새 자료를 보고 다시
정해야 하기 때문이다.

**못 받으면 넘긴다.** 요소의 60~75%가 서류에 걸려 있어, 「못 받음」 한
번에 그 요소가 곧바로 미인정이 됐다. 서류가 맡던 KSA 를 면접·실기로
넘긴다(`stages.carry_over()`). 같은 요소에 아직 안 찍은 면접·실기 항목이
있으면 거기 얹고, 없으면 면접 항목을 새로 만든다. 이미 찍은 항목에는
얹지 않는다 — 그 KSA 는 확인된 적이 없기 때문이다.

**「미실시」는 통과가 아니다.** 아무것도 안 하고 인정이 되고 있었다.
미통과와 같이 「확인되지 않음」으로 센다.

### 고르는 말은 「그 다음에 무슨 일이 일어나나」로 정한다

2단계에 「받음 / 못 받음 / 미실시」 세 개를 두었더니 「미실시가 뭐냐」는
질문을 받았다. 서류는 받았거나 못 받았거나 둘 중 하나다. 「요청하지 않음」은
아직 아무것도 안 누른 상태와 같아 따로 둘 이유가 없었다.

| 단계 | 고를 수 있는 것 | 그러면 |
|---|---|---|
| 2 추가 서류 | 받음 | 이 서류로 확인되는 것이 채워진다 (파일을 올리면 다시 판정) |
| | 못 받음 | 이 서류가 맡던 것이 면접·실기로 넘어간다 |
| 3 면접 | 확인됨 / 확인 안 됨 / **면접 안 함** | 안 하기로 정하는 것은 실제 판단이다 — 확인되지 않은 것으로 본다 |
| 4 실기 | 확인됨 / 확인 안 됨 / **실기 안 함** | 위와 같다 |

버튼마다 그 아래에 무슨 일이 일어나는지 한 줄씩 적는다. 예전에 기록된
값(「미실시」 등)이 있으면 지우지 않고 「예전 기록」으로 남긴다 — 아무 버튼도
안 켜져 있으면 저장이 안 된 것처럼 보인다.

### 하나를 찍으면 화면 전체가 따라 움직인다

찍어도 인정 시간·히트맵·단계 진척이 그대로면 「저장이 안 된다」로 읽힌다.
저장한 뒤 같은 주소를 다시 받아 `section.dash` · `.steps` · `.bar3` 만
바꿔치기한다. 화면이 두 벌로 계산하면 반드시 어긋나므로, 서버가 그린
그대로를 가져온다.

**정말로 안 바뀌는 자리는 그렇다고 적는다.** 대상 요소가 이미 정해졌으면
(1단계 인정·불인정, 또는 훈련 항목이 걸려 확인으로 풀리지 않음) 무엇을
눌러도 인정 시간이 달라지지 않는다. 실측 R2026-9002 는 27개 요소가 전부
그랬다 — 인정 17(전문가 8 + 기록 확정 9) · 불인정 8 · 조건부인정 2(훈련
항목이 걸려 미인정). 항목마다 그 사실과 되돌리는 길을 적는다.

### 숫자를 말하는 자리는 하나다

같은 값을 두 곳에서 세면 반드시 갈라진다. 시험 지원자 C002(과정평가형
자격 보유) 한 건을 처음부터 끝까지 돌려 보니 네 군데가 갈라져 있었다.

| 갈라진 곳 | 무엇이 어긋났나 | 어떻게 모았나 |
|---|---|---|
| 진행률 | 판정은 한글 열쇠(전체·완료·단계)로 적는데 화면은 영어(total·done·phase)로 읽어 능력단위 7개를 도는 내내 「0/1」 | `Run.steps` 하나로 읽는다 |
| 개요 막대 vs ① 칸 | 막대가 요소에서 다시 세느라 자격 편성시간을 못 봐 「기록 100시간」, ① 칸은 「320시간」 | `ReviewContext.credited_units` — 기록 확인 결과를 그대로 쓴다 |
| 5단계 화면 vs 최종 판정 기록 | 화면 370시간, 기록은 「확정 150 · 조건부 350」 | `record_decision` 이 다섯 단계 결과를 기본값으로 쓰고 `credit_basis.검토결과` 에 남긴다 |
| 목록 vs 개요 | 목록이 요소 전체로 세어, 다 끝낸 건이 「22/30」으로 남아 보임 | 판단 대상으로 센다 |

**비용도 합쳐서 말한다.** 추가 서류로 다시 판정한 건은 마지막 실행분만
보이면 실제보다 싸 보인다 — 실측 $0.60 으로 보였지만 처음 판정까지 합치면
$3.25 다.

**최종 판정이 났으면 그것이 답이다.** 막대는 판정된 시간을 보여 주고,
검토 계산과 다르면 그 차이도 적는다 (「검토 계산은 370시간이었고, 심사위원이
70시간을 빼고 정했습니다」).

### 단계마다 「마감」 하나 — 손대는 것은 된 것뿐

항목마다 「받음/못 받음/미실시」를 찍게 했더니 이런 말을 들었다 —
「파일 올리면 받은 거고 아니면 못 받은 건데 왜 일일이 체크하나」. 맞는
말이다. 시스템이 모르는 것은 **언제 기다리기를 그만두는지**뿐이다.

| 단계 | 사람이 하는 일 | 마감하면 손대지 않은 것 |
|---|---|---|
| 1 인정 여부 | 권고와 **다르게 볼 것만** 고른다 | **AI 권고대로** 확정 |
| 2 추가 서류 | 받은 서류를 **올린다** (버튼 없음) | 못 받음 → 면접·실기로 이월 |
| 3 면접 | 통과한 것만 누른다 (버튼 하나) | 미통과 |
| 4 실기 | 통과한 것만 누른다 (버튼 하나) | 미통과 |

**1단계 기본값이 왜 AI 권고인가.** 실측 R2026-0004 에서 심사위원이
2·3·4단계를 다 돌고도 최종 결과가 **0시간**이었다. 1단계를 한 번도 누르지
않았기 때문이다 — 보완 항목 결과는 「조건부인정」인 요소에만 효력이 있는데
그 요소가 하나도 없었다. 화면은 아무 말도 하지 않았다.

권고를 기본값으로 두면 사람은 다르게 볼 것만 고르면 된다. **마감 버튼이
사람의 서명이다** — 무엇을 그대로 채택했는지 감사 산출물(`N단계_마감`)과
`audit_log` 에 남는다. 마감 뒤 R2026-0004 는 인정 90/365시간으로 움직였고
원장의 「아직 정하지 않음」이 0이 됐다.

### 면접 항목에는 질문이 있어야 한다

실측 R2026-0004 의 면접 11건에 **질문이 하나도 없었고**, 내용도 서류 요청
(「편성표와 평가결과 확인서」, 「보험 가입증서」)이었다. 지침이 `oral_check`
를 실기에만 요구하고 면접에는 요구하지 않았기 때문이다.

지침을 고쳤고(면접도 질문 3~5개 필수, `item` 에 서류 이름 금지), 검증에
`면접_질문없음` 을 넣었다. 지금까지 나온 산출물이 다 그러므로 **경고**로
둔다 — 오류로 두면 옛 판정이 통째로 막힌다. 화면은 질문 없는 면접 항목에
「질문이 만들어지지 않았습니다」라고 적고 KSA 목록을 대신 보여 준다.

### 최종 판정은 「인정 원장」이다

5단계 「최종 결과」에 요소 서른 줄짜리 표 하나뿐이었다. 근거는 되지만
종합이 아니다. 심사위원이 서명 직전에 알고 싶은 것은 「420시간이 어디로
갔나」다.

**규칙 하나 — 총 필수 시간의 1시간도 빠짐없이 정확히 하나의 경로에 속한다.**
합이 다르면 화면이 「이 값을 쓰지 마십시오」라고 말한다.
계산은 `services/review/ledger.py` 한 자리.

| 경로 | 뜻 | 어느 단계에서 |
|---|---|---|
| 기록으로 인정 | 자격 편성시간·훈련이수증으로 갈음 | ① 기록 확인 |
| 제출 서류로 인정 | 낸 자료만으로 요소가 모두 인정 | ③-1·③-2 |
| 면접으로 확인 | 확인했거나 확인할 것 | ③-3 |
| 실기로 확인 | 확인했거나 확인할 것 | ③-4 |
| 훈련으로 채워야 함 | 확인으로 풀리지 않음 | ③-1 |
| 아직 정하지 않음 | 1단계 판단이 남음 | ③-1 |

능력단위가 한 줄이고, 줄마다 **시간 · 상태 · 근거 한 줄 · 원본으로 가는
길**(기록 확인 보고서 / AI 응답 원본 / 감사 기록)이 붙는다. 면접과 실기가
한 단위에 섞이면 요소가 많은 쪽(같으면 실기)에 한 번만 넣고 줄에는
「면접 2 · 실기 2」로 둘 다 적는다 — 두 번 세지 않으면서 숨기지도 않는다.

**판정 입력도 여기 있다.** 예전에는 옛 검토 화면 하단 바에만 있었고, 그
화면은 1단계 판단만 세는 또 다른 계산을 써서 같은 건에 350시간이라고 적었다
(5단계는 370시간). 인정 시간에는 계산값이 미리 들어가고, 사람이 바꾸면 그
차이가 판정 기록에 함께 남는다.

**판정자 칸은 없다.** 이 앱은 심사위원 개인이 아니라 **합의된 결론**을 받아
적는다. 적는 것은 판정·인정 시간·사유뿐이고, 기록에는 「심사위원 합의」로
남는다.

### 판정은 이력으로 쌓는다

`final_decision` 은 접수 건마다 한 줄이라 다시 기록하면 덮인다. 예전에는
감사 산출물까지 같은 이름으로 덮어써서, 「370시간으로 정했다가 300시간으로
바꿨다」는 사실은 남는데 **첫 판정의 근거는 사라졌다.**

이제 판정마다 `최종판정_N회` 로 따로 남기고, 회차는 **판정 횟수**로 센다
(산출물 개수로 세면 예전에 빠진 것 때문에 번호가 밀린다). 5단계 화면이
회차·판정·인정 시간·계산값·판정자·근거 링크를 표로 보여 준다.

**판정 뒤에 결과가 바뀌면 말한다.** 면접·실기 결과가 판정보다 나중에
들어오면 머리에 「기록된 판정은 300시간인데 지금 계산은 370시간입니다 —
다시 기록하십시오」가 뜬다.

### 집었다는 표시는 따로 커밋한다

「판정 워커가 돌고 있지 않습니다. 시작은 기록됐지만 아무도 집어 가지
않습니다」 — 워커가 **바로 그 작업을 돌리는 중**인데 화면이 그렇게 말했다.

`run_once` 가 집는 것과 처리하는 것을 한 트랜잭션에 묶고 있었다. `dequeue`
가 쓴 `status='running'` 과 `locked_at` 은 핸들러가 끝나야 커밋되므로, 판정이
도는 6~30분 내내 밖에서는 그 작업이 `queued` 로 보이고 `locked_at` 은 비어
있었다. 죽으면 `running` 인 채로 남지만 그것은 `reclaim_stale()` 이 맡는다.

**「워커가 없다」고 말하는 기준도 손봤다.** `worker_alive` 는 「최근에 작업을
집었나」를 보므로 ① 놀던 워커는 살아 있어도 흔적이 없고 ② 한 작업을 30분
도는 동안 새로 집는 일이 없다. 그래서 **지금 돌고 있는 작업**도 함께 보고
(회수 한계 안이면 살아 있는 것으로), 화면은 **넣은 지 30초가 지나야** 멈췄다고
말한다. 실측으로 큐에 넣은 지 1초 만에 `running` 이 되고 워커가 살아 있는
것으로 보인다.

### 화면 스크립트는 node 로 실제로 돌려 본다

`mark(btn, box)` 로 매개변수를 늘리면서 함수 안의 `const box` 와 이름이
겹쳤다. 그 한 줄에 **스크립트 전체가 파싱을 못 해** 3·4단계의 결과 저장과
판정 기록이 통째로 죽었다. 화면은 200 을 돌려주고 버튼도 그대로 있어
아무도 몰랐다. `$` 헬퍼가 없어 `decide()` 가 첫 줄에서 죽은 적도 있다.

파이썬 시험으로는 문자열 안의 문법 오류를 잡을 수 없다. `node --check` 로
모든 화면의 스크립트를 검사하고, 껍데기 DOM 을 씌워 버튼 손잡이를 실제로
불러 본다(`tests/integration/test_page_scripts.py`).

### 시간은 갈음됐는데 요소는 미인정인 단위

과정평가형 자격의 편성시간이 요구시간을 갈음하면 그 단위의 시간은 붙는다.
그런데 같은 단위의 요소를 전문가가 「담당한 적 없다」는 진술을 근거로
미인정으로 정할 수 있다. 실측 R2026-9010 에서 흡·배기제어장치 30시간과
휠·얼라인먼트 40시간이 그랬다.

어느 쪽을 따를지는 정책이고 아직 정해지지 않았다. 그러니 조용히 한쪽으로
넘기지 않고 5단계 화면과 판정 기록(`credit_basis.검토결과.갈음됐으나_요소미인정`)
양쪽에 내민다. 심사위원이 최종 판정에서 시간을 직접 지정해 정리한다.

### 결과를 더 바꾸지 못하는 보완 항목은 세지 않는다

1단계에서 전문가가 「불인정」으로 정해 버린 요소에도 면접·실기 항목이 붙어
있다. 그것을 그대로 세면 그 단계가 영영 끝나지 않는다 — 무엇을 찍어도 인정
시간이 달라지지 않는데 화면은 계속 남았다고 말한다. 실측 R2026-9002 에서
면접 1건·실기 4건이 그랬고, 그래서 「최종」으로 넘어갈 수 없었다.

`stages.is_live()` 가 가른다 — 대상 요소 가운데 하나라도 「대기」면 살아
있는 항목이다. 세지 않은 것도 감추지는 않는다. 단계 화면 아래에 「결과가 더
바뀌지 않는 항목」으로 접어 두고, 되돌리는 길(1단계에서 조건부인정으로
바꾸기)을 적는다.

### 면접 질문지·실기 과제는 개요에서 바로 열린다

「검토하기」 링크 하나만 있으면 어디에 무엇이 있는지 알 수 없다. 개요의
③ 칸에 다섯 단계를 줄로 늘어놓고, 무엇이 들어 있는 단계인지 이름을 붙인다.

    1 인정 여부 검토 18/18 완료 · 2 추가 서류 · 요청할 서류 7/7 완료
    3 면접 · 면접 질문지 1건 · 결과 안 바뀜 · 4 실기 · 실기 과제 4건 · 결과 안 바뀜
    5 최종 결과 보기

### 판단 어휘의 뜻은 기준서에 있다

「인정·조건부인정·불인정·보류」가 각각 무슨 뜻인지 어디에도 적혀 있지
않으면 사람마다 다르게 쓴다. 이건 정책이므로 `config/rubric/v0.2.yaml` 의
`final_decision.element_decision_meanings` 에 두고 화면이 그대로 읽어 온다.

### 요소 이름은 기준에서 가져온다

AI 가 되풀이해 준 이름에 기대면 안 된다 — 판정 4건 중 2건은 33·30개 요소
전부에서 이름이 빠져 화면에 코드만 떴다. `catalog_ncs_element` 에서 찾는다.

### 판정이 도는 동안 진행률이 보인다

판정 한 건은 6~28분 걸린다. 그동안 화면이 「판정 중」만 보여 주면 멈춘 것과 구분되지 않는다.

```
가금사육_L3   ▓▓▓▓░░░░░  분석 4/9 · 가금 방역관리 외 2
```

**본 트랜잭션 안에서는 진행률을 적을 수 없다.** 판정은 한 트랜잭션에서 도는데
그건 끝나야 커밋되므로, 같은 세션으로 적어도 밖에서는 아무것도 안 보인다.
실제로 그렇게 만들었다가 `UPDATE` 가 0행에 적용되고 조용히 넘어갔다. 그래서

- **판정 행을 먼저 따로 커밋한다** — 도중에 죽어도 흔적이 남는다
- 진행률은 청크가 끝날 때마다 **별도 세션에서 즉시 커밋**한다 (`set_progress`)
- 0행 갱신은 경고로 남긴다 — 이 버그가 그렇게 숨어 있었다
- 화면은 `/cases/progress.json` 만 3초마다 긁어 **그 줄만** 고친다.
  통째로 새로고침하면 스크롤이 튀고 열어 둔 것이 닫힌다
- 도는 건이 없으면 30초 간격으로 늦춘다

### 검토 화면은 「다 읽지 않아도 되게」 묶는다

요소 33개를 통째로 펼쳐 놓으면 어디부터 볼지 알 수 없다. 손이 가는 정도로 나눈다.

| 묶음 | 뜻 | 실측(R2026-0002) |
|---|---|---|
| **먼저 보실 것** | 결정과 **어긋나는 자료**가 있다 | 4개 |
| 판단이 필요한 것 | 근거를 보고 정하면 된다 | 17개 |
| 기록으로 확정된 것 | 훈련이수증에 코드·시간·평가결과가 있다. 확인만 | 12개 |

「부정 진술이 있음」만으로 고르면 33개 중 17개가 걸려 선별이 되지 않는다.
정작 봐야 할 것은 **기록으로 기이수 확정됐는데 「그 자세는 담당한 적 없다」는 진술이 붙은 것**이다.

- 묶음은 기본으로 접혀 있고, 요소 줄을 누르면 근거가 펼쳐진다
- 묶음마다 **일괄 처리** 버튼 — 「기록으로 확정된 것 12개 전부 인정」이 한 번에 된다
  (`POST /assessments/{aid}/reviews` 가 한 트랜잭션으로 처리하고 감사 기록도 한 번만 남긴다)

**빌드 도구가 없다.** FastAPI 가 HTML 을 만들어 내보내고 필요한 곳만 바닐라 JS 를 쓴다.
`node_modules` 도 번들러도 없으므로 배포는 파이썬 프로세스 하나다.
나중에 **채팅 방식 검토 요청**을 붙일 때도 이 구조가 그대로 맞는다 —
스트리밍은 `StreamingResponse`(SSE), 메시지 추가는 지금 검토 화면이 쓰는
`fetch` → DOM 갱신 방식과 같다.

### 화면은 공통 껍데기 하나를 쓴다

`services/report/layout.py` 에 색·간격·머리말이 한 벌 있다.
화면마다 CSS 를 복사해 붙이면 곧 서로 어긋나므로, 각 화면은 자기 것만 얹는다.

### 받는 파일 형식은 파서가 정한다

`storage.allowed_extensions` 는 기동 시 파서가 읽을 수 있는 형식인지 대조하고,
어긋나면 뜨지 않는다. 한때 8개 중 5개(docx·xlsx·jpg·jpeg·png)를 받도록 해 두었는데
파서는 못 읽어서, 올린 담당자가 「조각 0개」를 보고서야 알았다.
지금은 `pdf · hwp · hwpx · txt · md` 만 받고, 이미지는 OCR 을 붙인 뒤에 연다.

### 워커가 죽으면 화면이 알려 준다

작업을 집는 순간 `running` 으로 바꾸고 커밋하므로, 그 뒤 워커가 죽으면
**작업은 잡힌 채로 남는다.** 실제로 8시간 넘게 방치된 적이 있고,
그동안 화면은 워커가 살아 있다고 표시했다.

- `worker_alive()` 는 `status='running'` 이 아니라 **최근에 잠긴 흔적**을 본다
- `reclaim_stale()` 이 워커 기동 시와 5분마다 오래 잡힌 작업을 도로 대기로 돌린다
- 대시보드가 「멈춰 있는 작업」을 그대로 띄운다
- 대상이 사라진 작업은 **재시도하지 않고 바로 접는다** — 세 번 더 돌려도 결과가 같다

## 전문가 검토 (4단계)

```
GET  /assessments/{aid}/review              검토 화면 (HTML)
GET  /assessments/{aid}/review/summary      진행 상황·감면 시간
POST /assessments/{aid}/elements/{eid}/review   요소별 의견 저장
GET  /assessments/{aid}/reviews             저장된 의견 목록
POST /submissions/{sid}/decision            최종 판정 기록
GET  /submissions/{sid}/decision            기록 조회
```

```bash
./scripts/dev.sh api                     # 서버 기동
./scripts/dev.sh review                  # 실사례 4건에 가상 검토를 채운다 (--clear 로 지움)
# http://localhost:8000/assessments/{판정번호}/review
```

### 화면이 하는 일

한 요소를 판단하는 데 필요한 것이 **한 화면 안에** 있다.

```
권고(뜻을 붙여 표기) → 사유 → 근거 인용 → [원문] → 소속·기간 뒷받침
→ 기이수 → 부정 진술 → 빈 항목 → 채우는 방법 → 자료 간 어긋난 부분 → 소견
→ [인정] [조건부인정] [불인정] [보류] + 메모
```

인용문 옆 **「원문」**을 누르면 제출 자료의 해당 조각이 그대로 펼쳐진다.
AI가 요약한 것이 아니라 원본과 대조할 수 있어야 하기 때문이다.

읽는 사람은 RPL·직종 전문가다. 화면에는 내부 용어를 쓰지 않는다
(`evidence_level`·`confidence` 같은 필드명은 노출되지 않는다 — 시험으로 막아 둔다).
권고 코드 R0~R5 는 기준서에 있는 말이라 남기되 **항상 뜻을 붙여** 쓴다.

### 사람 의견은 AI 산출물을 덮어쓰지 않는다

`element_review` 에 따로 쌓이고, 저장 시점의 AI 권고를 함께 적는다.
나중에 「기계는 R3 라 했는데 사람은 인정했다」를 셀 수 있어야 하기 때문이다.

### 감면 시간 — 요소 단위 검토를 능력단위 단위로 접는다

Track B 는 **능력단위요소** 단위로 검토하지만 훈련시간은 **능력단위** 단위로 편성된다.
둘을 잇는 규칙이 `rubric.final_decision.unit_credit_rule` 이다.

| 규칙 | 뜻 |
|---|---|
| `all_elements` (기본값) | 요소가 **전부** 인정되어야 그 능력단위 시간을 감면 |
| `proportional` | 인정된 요소 **비율만큼** 감면 |

⚠ 이 규칙은 아직 확정되지 않았다(**D-7**). 그래서 **두 방식을 모두 계산해** 화면에 나란히 놓는다.
조건부인정은 면접·실기를 통과해야 확정되므로 확정분과 나누어 센다.

실사례 4건 (AI 권고를 그대로 따른 가상 검토):

| 심사번호 | 검토 | 감면(확정) | 조건부 포함 | 비율 규칙이면 | 권고안 |
|---|---|---|---|---|---|
| R2026-0001 | 27/27 | 0 / 205시간 | 185시간 | 0 → 185시간 | 불인정 |
| R2026-0002 | 33/33 | **190** / 410시간 | 270시간 | 190 → 322시간 | 부분인정 |
| R2026-0003 | 23/23 | **168** / 348시간 | 268시간 | 168 → 288시간 | 부분인정 |
| R2026-0004 | 30/30 | 0 / 365시간 | 90시간 | 59 → 270시간 | 불인정 |

규칙에 따라 조건부 포함 감면이 **90시간과 270시간**만큼 갈린다(R2026-0004).
간담회에서 결정할 값이 무엇을 바꾸는지 이 표가 그대로 보여준다.

### 최종 판정은 시스템이 하지 않는다

- 요소 검토를 **모두 마쳐야** 기록 버튼이 열린다 (`allow_incomplete` 로 예외 가능)
- 시스템은 **권고안**만 낸다. 사람이 다른 값을 골라도, 감면 시간을 직접 써넣어도 된다
- 기록에는 **계산식 전체**가 함께 남는다 (`final_decision.credit_basis`) —
  규칙·능력단위별 인정 현황·다른 규칙 적용 시 값·그 시점의 미확정 기준 목록.
  몇 시간이냐보다 **왜 그 숫자냐**가 분쟁에서 중요하다

## 감사 추적 (5단계)

**「잘 됐습니다」를 믿지 않아도 되게 하는 것**이 이 단계의 목적이다.
각 단계가 실제로 무엇을 받아 무엇을 내놨는지 **그때 그대로 파일로 남긴다.**

```
storage/audit/{심사번호}/
  ingest/   01_문서목록  02_마스킹기록  03_조각  04_기이수추출
  판정{N}/
    package/   01_AI입력패키지  02_분석지침  03_기준요약
    llm/       10_1차_AI응답  (20_2차_AI응답 …)  98_실행요약  99_최종채택_요소
    validate/  10_1차_검증결과  (11_1차_재요청 …)
    review/    01_요소별검토
    decide/    01_최종판정
```

파일은 손대지 않는다. 다시 돌리면 새 `판정{N}` 폴더가 생긴다.
DB 의 `artifact` 표는 **색인일 뿐**이다 — 무엇이 언제 어떤 해시로 만들어졌는지.

### 한 번에 돌려 보고 확인하기

```bash
./scripts/dev.sh walk        # ①→⑥ 전 단계 실행 + 남은 산출물 + 해시 대조
./scripts/dev.sh api         # http://localhost:8000/audit
```

| 보는 방법 | 명령 |
|---|---|
| 화면 (전체 목록) | `http://localhost:8000/audit` |
| 화면 (한 건 단계별) | `http://localhost:8000/audit/R2026-0002` |
| 화면 (운영 통계) | `http://localhost:8000/stats` |
| 터미널 (단계별 요약) | `./scripts/dev.sh audit R2026-0002` |
| 터미널 (내용 출력) | `./scripts/dev.sh audit R2026-0002 --show 조각` |
| 터미널 (해시 대조) | `./scripts/dev.sh audit R2026-0002 --verify` |
| 기계 판독 (해시 목록) | `GET /submissions/{sid}/manifest` |
| 파일 직접 | `storage/audit/R2026-0002/` |

### 위·변조는 드러난다

저장할 때 sha256 을 함께 기록한다. 파일을 열 때마다 다시 계산해 대조하므로,
나중에 누가 고쳐 넣으면 화면과 CLI 양쪽에서 **⚠ 해시 불일치**로 드러난다.

```
[1395] 조각   7KB 3ce3571575  ⚠ 해시 불일치
대조 결과: 12/13 일치 · ⚠ 어긋남 1건
```

### 개인정보는 기록에 남기지 않는다

마스킹 **이전** 원문은 저장하지 않는다. 저장하면 마스킹한 의미가 없다.
대신 「어디서 어떤 유형이 몇 글자 가려졌는지」를 값 없이 남긴다.

```json
{"유형": "전화번호", "줄": 3, "가려진_글자수": 13, "앞": "담당 연락처 ", "뒤": " 입니다"}
```

가려진 값이 기록에 새어 나오지 않는지는 시험으로 막아 둔다
(`test_masking_record_never_keeps_the_value`).

### 기록은 실제 결과와 대조된다

산출물이 그냥 남아 있는 것으로는 부족하다. 시험이 **일치 여부**를 확인한다.

| 확인 | 시험 |
|---|---|
| 조각 파일 = DB 의 조각 | `test_fragment_record_matches_database` |
| 저장된 패키지 해시 = 판정 기록의 `input_hash` | `test_package_record_is_what_was_sent` |
| AI 응답은 정규화 **이전** 원본 | `test_ai_response_is_raw` |
| 최종 판정의 능력단위별 감면 합 = 기록된 감면 시간 | `test_decision_record_carries_the_arithmetic` |
| 기록된 모델 = **실제로 응답한** 모델 | `test_execution_record_names_the_real_model` |

마지막 항목은 실제로 버그였다. `assessment.model` 에 **설정된** 모델을 적고 있어서,
재생(replay)으로 돌린 것이 `claude-opus-5` 가 돌린 것처럼 남았다.
지금은 응답한 쪽(`replay:claude-opus-5`)을 적는다.

### 시험은 운영 보관함을 건드리지 않는다

시험을 돌릴 때마다 실제 심사 산출물이 늘어나면 감사 자체를 믿을 수 없다.
`tests/conftest.py` 가 `KRPL_ENV=test` 를 세워 `storage/_test/` 로 보내고,
시험 시작 시 그 폴더만 비운다. `storage/audit/` 는 손대지 않는다.

### 운영 통계

`GET /stats` (화면) · `GET /stats.json` (기계 판독)

접수 현황 · **1차 검증 통과율**(재요청 없이 통과한 비율) · 평균 시도 ·
**AI 권고와 사람 판단의 일치율** · 누적 비용 · 토큰 · 검증에 걸린 항목 · 권고 분포 · 큐.

일치율이 낮다고 나쁜 것이 아니다. 사람이 실제로 다르게 판단하고 있다는 뜻이고,
그 차이는 감사 화면의 「AI 권고와 다르게 판단한 요소」 표에서 건별로 볼 수 있다.
